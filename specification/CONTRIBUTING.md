# Contributing

This guide describes how to contribute to this project while maintaining
traceability between requirements, epics, features, scenarios, tasks, code,
and tests.

## Before Contributing

- Read `.project.yml`, which is the source of truth for project configuration.
- Review the applicable instructions in `.github/instructions/`.
- Read the [Project Trace Kit usage guide](projecttrace-guide/UsageGuide.md) and the
  [analyst guide](analyst-guide.md).
- Keep project documentation and requirements specific to this destination project.
- Do not include secrets, caches, or generated output. The exceptions are the
  requirements index (`paths.requirements_index`) and `epics-consolidated.md`:
  they are versioned, regenerated by their scripts, and never edited by hand.

## Contribution Workflow

1. Create a descriptive branch, for example `<workflow.analyst_branch_prefix>name`
   (default `analyst/name`) or `feature/task-id-description`.
2. Make changes while preserving existing identifiers and traceability.
3. Update the documentation or templates affected by the change.
4. Validate the changes as described in
   [Validation and Checklist](projecttrace-guide/harness-reference.md#validation-and-checklist).
5. Open a Pull Request against the configured target branch
   (`repository.pull_request_target`) with a description of the change and validation
   evidence.
6. Wait for the required review and approval; do not commit directly to the base branch
   (`repository.default_branch`) or merge your own Pull Request.

The requirements workflow follows this sequence of `workflow.stages`
identifiers:

```text
specify -> analyze -> plan -> approve -> create_tasks -> implement -> test -> trace
```

## Change Rules

- Do not change existing IDs; create new ones when appropriate.
- Respect `requirements.mode` and the paths defined in `.project.yml`.
- Use only repositories, states, priorities, fields, and values defined in the configuration.
- Keep implementation, E2E verification, and test results separate.
- Do not mark a requirement, task, or scenario as complete without evidence.
- Update the change history when modifying requirement artifacts.
